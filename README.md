# agent — первый CLI-агент с инструментами

Интерактивный чат-агент на Go. Пользователь пишет запрос в консоль, агент
отправляет его в LLM, сам решает, какой инструмент вызвать, получает результат
и формулирует финальный ответ. Цикл повторяется, пока модель не перестанет
запрашивать инструменты.

Базовая реализация выросла из `task1-05`: оттуда взяты HTTP-клиент
OpenAI-совместимого API, работа с `usage` и список задач `tasks.txt`.
Финальный отчёт-бенчмарк (`report.go`) в агенте не используется — вместо него
консольный чат.

## Запуск

```bash
export LLM_BASE_URL="https://..."
export OPENAI_API_KEY="..."

./run.sh                 # интерактивный чат
./run.sh -script testdata/checks.txt   # три проверки из задания
./agent -list-models
./agent -list-sessions
./agent -continue     # продолжить последнюю сессию
./agent -print-session 20261111-204115-1820   # весь лог сессии, офлайн
./agent -print-session last                   # то же для последней
```

`-print-session` читает только `session.jsonl` с диска: ни сети, ни ключей,
ни модели не нужно. Печатает хронологически все сообщения полным текстом,
вызовы инструментов (`→ calc(...)`, `← calc: 4`), события сжатия и смены
моделей; в заголовке — модели, с которыми сессия закончила.

Флаги: `-model`, `-summary-model`, `-session`, `-continue`, `-data`,
`-max-steps`, `-max-prompt-tokens`, `-reserve-output`, `-min-tail-tokens`,
`-max-tool-chars`, `-temperature`, `-max-tokens`, `-system`, `-script`,
`-no-reasoning`, `-profile`, `-skip-profile`, `-print-session`.
Модели по умолчанию берутся из `LLM_MODEL` / `LLM_SUMMARY_MODEL`.
`run.sh` сам подхватывает `~/.env`, если переменные не экспортированы.
Если `LLM_SUMMARY_BASE_URL` не задан и локальный Ollama отвечает на
`localhost:11434`, `run.sh` направляет сжатие и проверку инвариантов на
`qwen2.5:14b`; иначе они идут на чат-клиент (`opencode`).

`-script` выполняет файл построчно: обычные строки уходят модели, строки с `/`
выполняются как команды чата. Так записываются воспроизводимые демо — см.
`testdata/day11-demo.txt` (реплики, `/memory`, `/memory clear knowledge`, вопрос).

## Инструменты

| Инструмент | Аргументы | Что делает |
|---|---|---|
| `now` | — | текущее время (локальное и UTC) |
| `calc` | `{"expr": "..."}` | арифметика `+ - * /` и скобки, без `eval` |
| `find_riddle` | `{"query": "..."}` (пусто — список всех) | поиск загадки по `tasks.txt` из дня 5 |

Схемы инструментов отправляются в запросе в поле `tools` (JSON Schema), модель
сама выбирает имя и аргументы. `tool_choice: "auto"`, `parallel_tool_calls` не
используется — шаги идут последовательно, чтобы результат одного инструмента
мог стать аргументом следующего.

## MCP: внешние инструменты

Помимо локальных инструментов агент умеет подключать MCP-серверы. Это общая
настройка, не привязанная к демо: `mcp.json` ищется по `-mcp-config` →
`MCP_CONFIG` → `./mcp.json` → `~/.config/goagent/mcp.json` → `<data>/mcp.json`,
а `-no-mcp` выключает MCP полностью.

```json
{
  "version": 1,
  "approval": "ask",
  "servers": [
    {
      "name": "fs",
      "command": "uvx",
      "args": ["--from", "filesystem-mcp", "filesystem-mcp", "${MCP_FS_ROOT}"],
      "allow": ["read_file", "list_directory", "list_allowed_directories"],
      "approval": {"list_allowed_directories": "allow", "read_file": "ask"},
      "rules": {"read_file": {"path_under": "${MCP_FS_ROOT}"}}
    }
  ]
}
```

Инструмент сервера регистрируется как `mcp_<server>_<tool>` и уходит в модель
обычной функцией — в схеме нет поля «источник». Код маршрутизирует вызов по
префиксу: локальные имена идут в `Run`, MCP-имена — в `ClientSession.CallTool`.

Апрув выполняется кодом до вызова: `allow` — сразу, `deny` — запрет, `ask` —
вопрос `y/n/a` в TTY. В `-script` по умолчанию `deny`; для демо нужен
`-mcp-approval=allow`. Аргументы проверяются отдельно: путь не выходит за
`path_under`, URL — только http/https и домены из `url_hosts`.

`-dump-request <path>` пишет NDJSON с телами запросов к модели: видно, что
локальные и MCP-схемы ушли в одном `tools`. Подробнее — `MCP.md`.

Ответ MCP считается недоверенным. По умолчанию `-mcp-guard=heuristic` убирает
управляющие символы и оборачивает результат в
`<untrusted_tool_output …>`, помечая типовые инъекции. `-mcp-guard=model`
дополнительно спрашивает модель сжатия, безопасен ли текст; при отказе
результат не попадает в промпт. `-mcp-action-guard=model` проверяет ещё и
намерение вызова перед апрувом. Это снижение риска, а не гарантия: основную
защиту дают allowlist, проверка путей/URL и подтверждение пользователя.

## Цикл агента

```
user → LLM → tool_calls → выполнение → role:"tool" → LLM → ... → финальный текст
```

`agent.go` хранит `assistant`-сообщение с `tool_calls` дословно (включая `id`) и
добавляет на каждый вызов по сообщению `role:"tool"` с тем же `tool_call_id`.
Ошибки инструментов и паники не роняют цикл: они возвращаются модели текстом,
чтобы она могла исправить аргументы. Защита от зацикливания — `-max-steps`.

## Модели

Список моделей из `task1-05` (`config.go`):

| Модель | Тип | $/1M (вход / выход) |
|---|---|---|
| `opencode-go/deepseek-v4.1-flash` | маленькая | 0.30 / 1.20 |
| `deepseek-v4-flash` | маленькая | 0.311270 |
| `glm-5.3-flash` | средняя | 0.788471 |
| `qwen3.8-27b` | флагман | 0.303003 |

Для `deepseek-v4.1-flash` шлюз отдаёт раздельные ставки: 0.30 за 1M входных
токенов и 1.20 за 1M выходных (чтение из кеша — 0.006). Старые id провайдер
тарифицирует одной смешанной ставкой, поэтому у них вход и выход равны.

Префикс провайдера в id — не украшение: шлюз opencode по нему решает, списывать
запрос с подписки или с pay-as-you-go кредитов. Без префикса та же модель
отвечает `402 Insufficient balance`. Кроме id шлюз требует заголовок
`x-opencode-session`; такие заголовки передаются без хардкода в коде —
`LLM_EXTRA_HEADERS="x-opencode-session: goagent-cli"` (несколько пар — через `;`).

Две роли:

- **чат-модель** — `-model`, команда `/model` или переменная `LLM_MODEL`;
  по умолчанию берётся `LLM_MODEL` из окружения, иначе первая модель списка
  (`opencode-go/deepseek-v4.1-flash`);
- **модель сжатия** — `-summary-model` или `LLM_SUMMARY_MODEL`, по умолчанию
  самая дешёвая в списке (`opencode-go/deepseek-v4.1-flash`). Сжатие вызывается редко и должно
  стоить меньше, чем экономит; если модель сжатия недоступна, сообщения
  всё равно архивируются, а в конспект пишется пометка.
- **эндпоинт сжатия** — `LLM_SUMMARY_BASE_URL` (необязательно): уводит конспект,
  факты и экстрактор памяти на другой сервер, например локальный Ollama, пока
  чат остаётся на платном API. Ключ — `LLM_SUMMARY_API_KEY` (по умолчанию
  `OPENAI_API_KEY`), заголовки — `LLM_SUMMARY_EXTRA_HEADERS`. Экстрактор
  вызывается на каждом ходу, поэтому локальное сжатие экономит и деньги, и
  лимиты провайдера.

Провайдер может отдавать не все id из списка (часть моделей способна
«повиснуть» на конкретном эндпоинте), поэтому рабочую модель удобно задать
через `LLM_MODEL`. Лимит ответа ограничен `-max-tokens` (по умолчанию 4096):
reasoning-модели тратят его сначала на скрытые рассуждения.

Смена чат-модели пишется в лог событием `model_switch`, поэтому при
продолжении сессии видно, чем отвечали.

## История: append-only JSONL

Одна сессия — один каталог и один файл:

```
$XDG_DATA_HOME/goagent/sessions/<session-id>/session.jsonl
```

Формат — event sourcing, одна JSON-запись на строку:

```jsonl
{"type":"session","v":1,"id":"20261110-233246-ab12","chat_model":"opencode-go/deepseek-v4.1-flash","summary_model":"opencode-go/deepseek-v4.1-flash","system":"...","created":"..."}
{"type":"message","message":{"seq":1,"role":"user","content":"Который час?","ts":"...","tokens_est":8}}
{"type":"message","message":{"seq":2,"role":"assistant","content":"","tool_calls":[{"id":"c1","type":"function","function":{"name":"now","arguments":"{}"}}],"ts":"..."}}
{"type":"message","message":{"seq":3,"role":"tool","content":"...","tool_call_id":"c1","name":"now","ts":"..."}}
{"type":"message","message":{"seq":4,"role":"assistant","content":"Сейчас 12:00.","ts":"..."}}
{"type":"compact","covers":[1,3],"summary":"Пользователь спрашивал время..."}
{"type":"model_switch","model":"glm-5.3-flash"}
```

Почему JSONL, а не один JSON: запись за O(1), без перезаписи файла; обрыв
процесса портит максимум последнюю строку (она пропускается с предупреждением);
файл читается глазами и через `grep`/`jq`. При старте события переигрываются,
и восстанавливаются активное окно, конспект и архив.

## Сжатие контекста

Бюджет: `-max-prompt-tokens` (6000) минус `-reserve-output` (1024). Перед каждым
запросом считается размер промпта; при заполнении выше 85% запускается сжатие.

Второй, независимый триггер — `-compact-every N` (по умолчанию 0, выключен):
сжатие срабатывает, как только после прошлого сжатия накопится N новых
сообщений (считаются все — `user`, `assistant`, `tool`), даже если бюджет ещё
не выбран. Дословный хвост после сжатия не считается: иначе при хвосте длиннее
N триггер срабатывал бы каждый ход. Что наступит раньше, то и запускает
сжатие; по счётчику делается один проход, по бюджету — до трёх, чтобы окно
гарантированно влезло.

1. **Усечение tool-выводов в промпте** до `-max-tool-chars` (800). Полный
   результат остаётся в логе.
2. **Скользящее окно** — последние ходы (не меньше `-min-tail-tokens`, 1200)
   остаются дословно. Граница окна всегда по сообщению `user`, поэтому пара
   `assistant` + `tool` никогда не рвётся.
3. **Rolling summary** — выпавший префикс сжимается дешёвой моделью в конспект
   до 250 слов; в конспект явно попадают конкретные детали — имена, числа,
   сроки, бюджеты, ограничения и принятые решения. Конспект добавляется в
   начало system-сообщения. Каждая попытка
   ограничена 75 с; если модель сжатия не ответила (503, таймаут, пустой
   ответ), конспект один раз пробует построить **чат-модель** — в консоли это
   видно строкой «сжатие: qwen… не справился (…) — пробую glm…».
4. **Слияние** — при следующем сжатии старый конспект сворачивается вместе с
   новым префиксом.

Посмотреть, что реально уйдёт в модель, можно командой `/context`: system
prompt, конспект (с диапазоном `seq`), дословный хвост и схемы инструментов —
каждый блок в токенах, плюс итог с калибровкой и текущий порог сжатия. Конспект
печатается целиком — видно, что именно осталось от свёрнутой истории.

## Стратегии контекста и ветвление

`-strategy <имя>` выбирает, как промпт помнит диалог; переключение на ходу —
`/strategy <имя> [N]`. По умолчанию — `summary` (раздел «Сжатие контекста»
выше).

| стратегия | память за окном | модельные вызовы на поддержку |
|---|---|---|
| `summary` (умолч.) | rolling-конспект из вытесненных ходов | 1 на сжатие |
| `window` | ничего — всё старше окна отбрасывается | 0 |
| `facts` | блок «ключ: значение» + последние N сообщений | 1 на каждый ход пользователя |

- **`window`** — `-window N` (обязателен): в промпте ровно последние N
  сообщений, окно сдвигается по одному сообщению (11-е сообщение вытесняет
  1-е, 12-е — 2-е и так далее). Граница сдвигается вперёд только если попала
  на `tool`-результат: он не может уйти в промпт без своего `assistant`-вызова.
  Вытесненное уходит в архив (событие `evict`) без конспекта —
  `/recall` найдёт текст, модель — нет. Ноль вызовов модели, ноль «знаний» о
  старых ходах: честное «отбрось и забудь».
- **`facts`** — `-window N` (обязателен): после каждого сообщения пользователя
  дешёвая модель (`-summary-model`, запасная — чат-модель) складывает детали в
  хранилище ключ-значение («срок: 15 декабря», «бюджет: 480 000 ₽»). Экстрактор
  возвращает обновлённый полный список JSON-объектом; не распарсилось или
  пусто при непустых прежних фактах — хранилище остаётся прежним, в консоли
  строка «факты: …». В запрос идут system + «Факты диалога» + последние N
  сообщений. Снапшот хранилища пишется в журнал событием `facts` и
  восстанавливается при повторном открытии сессии; посмотреть — `/facts`.

Окно в `window`/`facts` отсчитывается от текущего хода, поэтому промпт держится
около `system + факты + N сообщений` независимо от длины диалога. `/context` и
`/tokens` показывают активную стратегию, размер блока памяти и правило
вытеснения.

Память стратегий не мигрирует при переключении: конспект, оставшийся от
summary-фазы, в `window`/`facts` хранится в журнале, но в промпт не идёт —
статистика, `/history` и `/context` помечают его «(не в промпте)». Факты
начинают копиться с момента перехода в `facts` (историю экстрактор не читает),
а вытесненные окном сообщения в конспект уже не попадут. `/compact` в
`window`/`facts` не создаёт неиспользуемый конспект, а подсказывает перейти в
`summary`.

**Ветвление** — `/branch <имя>` сохраняет чекпоинт: копия текущего журнала
становится новой сессией `<имя>` с событием-ссылкой на родителя и точкой
(текущая сессия продолжает жить как исходная линия). Повторный `/branch <имя>`
существующей ветки переключается на неё, `/branch` без аргумента показывает
родителя, прямые потомки и текущую. Две ветки от одного места: `/branch B1`,
`/branch B2` из одной точки — дальше каждый ход пишется только в активную
ветку, а `/branch B1`/`/branch B2` прыгают между ними.

Токены оцениваются как `руны / 2.7` и калибруются по реальному
`usage.prompt_tokens` каждого ответа (EMA), поэтому бюджет подстраивается под
токенизатор провайдера без внешних зависимостей.

## Память: три слоя

`-strategy` управляет только краткосрочной памятью. Поверх неё работают два
долгоживущих слоя, и у каждого своё правило попадания в промпт:

| слой | что хранит | попадает в промпт |
|---|---|---|
| `short` | последние N сообщений дословно (+ конспект в `summary`) | окно целиком |
| `working` | карточка задачи: цель, ограничения, числа, сроки, бюджет, открытые вопросы, следующий шаг | всегда, ≤12 записей |
| `long.profile` | имя, роль, город, устойчивые предпочтения: стиль, формат, обращение, ограничения | всегда и последним блоком, ≤8 записей |
| `long.decisions` | принятые решения с датой | всегда, ≤12 записей |
| `long.knowledge` | адреса, контакты, цены, характеристики | только релевантные вопросу, до 6 |

- **Хранение раздельное.** Диалог — `data/<сессия>/session.jsonl`; рабочая
  память — `memory/working.json`; решения и знания — `memory/long.json`; профиль
  — общий `data/shared/profile.json` или именованный
  `data/profiles/<имя>/profile.json` (`-profile <имя>`). Файлы можно
  открыть и поправить руками, каждое изменение дублируется событием `memory` в
  журнале.
- **Что куда — решает модель.** После каждого сообщения
  пользователя дешёвый экстрактор (`-summary-model`) возвращает дифф по слоям:
  ограничения и числа — в рабочую память, «решили/выбрали» — в решения, адреса
  и телефоны — в знания, имя и предпочтения — в профиль; вопросы, эмоции и ход
  обсуждения не сохраняются никуда. Сломался экстрактор — память остаётся
  прежней.
- **Дифф умеет удалять.** `null` вместо значения (`{"working": {"ключ": null}}`)
  убирает запись: так факт переносится между слоями (открытый вопрос стал
  решением — появился в `decisions`, исчез из `working`) и убирается то, что
  стало неверным.
- **Лимиты в коде.** `memory.Caps` (12/8/12/20) не дают слою расти; при
  переполнении вытесняются самые старые записи.
- **Отбор знаний детерминированный:** слова вопроса от 4 символов ищутся в
  ключе и значении, берутся до 6 совпадений. Нет совпадений — слой в промпт не
  идёт.
- **Персонализация (день 12).** Профиль — отдельный файл на пользователя:
  `-profile кратко` берёт `data/profiles/кратко/profile.json`. В системный
  промпт он уходит последним блоком, поэтому предпочтения читаются после
  фактов; пополняется сам из реплик («пиши кратко», «без кода», «на ты» —
  ключи `стиль`, `формат`, `обращение`, `ограничения`), правится через
  `/profile`. Активный профиль печатается при старте — унаследованный из
  прошлой задачи не применяется молча. Если профиль пуст, при интерактивном
  старте агент задаёт три вопроса и пополняет профиль из ответов; для прогонов
  диалог отключается `-skip-profile`. Сам онбординг и правка предпочтения в
  диалоге показаны в `video/персонализация-день-12-онбординг.mp4`. Проверки и
  цифры — в [PROFILE.md](PROFILE.md).

- **Состояние задачи (день 13).** Задача — конечный автомат `planning →
  execution → validation → done` с таблицей переходов в коде: ассистент
  запрашивает этап инструментом `task_transition`, переход проверяется до
  применения, запрещённый возвращается ошибкой и состояние не меняется.
  «Нельзя делать реализацию до утверждённого плана» — флаг ставит только
  пользователь (`/task approve`), у модели такого действия нет. `/task pause`
  замораживает задачу на любом этапе, `/task resume` продолжает с того же
  шага; состояние — `task.json` рядом с журналом сессии, переживает
  перезапуск. Блок состояния уходит в каждый запрос после слоёв памяти, а
  сам инструмент ленивый: без начатой задачи его схемы в запросе нет.
  Автомат, гейты и пауза — в [TASK.md](TASK.md).

- **Устаревание и конфликты (день 15).** У каждой записи есть время последней
  записи (`updated_at`), его ставит код, а не модель. Противоречащий факт с тем
  же ключом **заменяет** старый, а не добавляется рядом; если пришли две записи
  одного ключа, побеждает более поздняя по времени. Замена, удаление и
  вытеснение попадают в журнал с парой «было → стало»: `/memory history`
  показывает, что и на что заменили. `/memory prompt` печатает ровно тот блок
  памяти, который уходит в системный промпт, поэтому видно, что старых
  значений в нём нет. После перехода задачи в `done` (инструмент или
  `/task state done`) код очищает `working`;
  `decisions` и `knowledge` остаются. У `decisions` ведущая дата в ключе
  отбрасывается кодом: экстрактор иногда копирует строку журнала целиком, и без
  этого замена не срабатывала бы. Демо и проверка — в [TASK.md](TASK.md)
  (отчёт дня 15).

`/memory` показывает слои, заполнение, время записи и токены, `/memory clear <слой>`
очищает слой, `/memory add <слой> ключ=значение` добавляет запись руками,
`/memory history [ключ]` показывает журнал «было → стало», `/memory prompt` —
точный блок памяти, который уходит в промпт.
`-memory-report <сессия>` печатает то же офлайн вместе с блоками промпта, а
`-import-memory <сессия> -session <новая>` переносит факты дня 10 в слои — той же
моделью, что и живой экстрактор (правил по ключевым словам нет).
Подробно — модель, правила, расход токенов и эксперимент с очисткой слоёв —
в [MEMORY.md](MEMORY.md).

## Инварианты проекта

Проектные ограничения — архитектура, стек, хостинг, бюджет — лежат в
`<data>/invariants.json`, **отдельно от диалога**. `/new` и `/session` их не
трогают; в файле рядом с набором хранится журнал изменений с парой «было →
стало»:

```json
{"invariants": [
  {"id": "db", "area": "database", "text": "Единственная СУБД — PostgreSQL 15",
   "rule": {"deny": ["mysql", "mongodb", "oracle"]}},
  {"id": "budget", "area": "budget", "text": "Не более 300 000 ₽/мес",
   "rule": {"max": 300000}}],
 "changes": [
  {"id": "budget", "kind": "change", "at": "…", "who": "user",
   "from": {"rule": {"max": 300000}}, "to": {"rule": {"max": 400000}}}]}
```

Правила машинные: `deny` — запрещённые подстроки, `allow` — exclusivity-список,
`max` — числовой предел (понимает `240 000 ₽`, `240 тыс`, `1,5 млн`). Набор
меняется только командой пользователя; у модели такого действия нет:

```
/invariant                                   список и файл
/invariant add db database deny=mysql,mongodb :: Только PostgreSQL 15
/invariant change budget budget max=400000 :: Не более 400 000 ₽/мес
/invariant remove host
/invariant history budget
```

**Проверка до выдачи ответа — два слоя.** Сначала модель обязана вызвать
`check_solution` и перечислить id затронутых инвариантов и конкретные выборы
(`area`, `value`). Код проверяет значения и требует, чтобы все затронутые
области были объявлены: не сослаться на инвариант нельзя. Затем свободный текст
ответа просматривает локальная модель с эндпоинта сжатия (`LLM_SUMMARY_*`,
например Ollama `qwen2.5:14b`) и возвращает `{violates,id,quote,reason}` — она
отличает «возьмите MongoDB» от «MongoDB использовать нельзя». Если локальный
эндпоинт недоступен, остаётся детерминированный поиск запрещённых терминов;
этот фолбэк виден в trace. Флаги: `-invariant-check llm|keywords`,
`-invariant-model <id>`, `-invariants <path>`.

Гейт в `Agent.Chat`: пока `check_solution` не пройден или текст не чист,
финальный ответ не отдаётся. Нарушающий черновик остаётся в `session.jsonl`
для аудита, в диалог добавляется служебная реплика `[проверка кода ·
инварианты] …`, и модель переписывает ответ; после трёх отказов ход
завершается ошибкой. При активных инвариантах стриминг ответа буферизуется
(в stdout нарушающий текст не попадает), reasoning продолжает идти. Блок
инвариантов стоит в системном промпте после памяти и перед задачей; `/context`
показывает его объём строкой `инварианты ~N ток.`.

Демо: `scripts/day14-demo.sh` (5 правил, 11 попыток обхода, смена бюджета
командой), проверка журнала — `scripts/check_invariants.py <data-dir>`.

## Токены и стоимость

Считаются на трёх уровнях:

- **текущий запрос** — `промпт ~X/6000` в футере после каждого ответа: оценка
  system + конспекта + активного окна (tool-выводы усечены так же, как в
  реальном запросе);
- **ответ модели** — `ответ ~N ток` из реального `usage.completion_tokens`
  (включая скрытые reasoning-токены);
- **вся история и накопленная стоимость** — `/tokens`: активное окно, архив,
  конспект, суммарные промпт/ответ/всего токены, деньги и модель сжатия;
  `/history` показывает оценку каждого сообщения активного окна.

Провайдер, который кеширует префикс промпта, возвращает в `usage`
`prompt_tokens_details.cached_tokens`. Такие токены считаются по кеш-ставке
(у `opencode-go/deepseek-v4.1-flash` это $0.006 вместо $0.30 за 1M — в 50 раз
дешевле), поэтому футер печатает `кеш 640/1729`, а `/tokens` — `промпт N (из
кеша M)`. Кеш включается сам, когда префикс запроса совпадает с предыдущим;
у opencode ключ кеша — заголовок `LLM_EXTRA_HEADERS="x-opencode-session: …"`,
поэтому одна и та же сессия переиспользует кеш, а новая — нет.

Как растут числа по ходу диалога (реальный прогон на glm-5.3-flash):

```
промпт ~507/6000  · ответ ~23   · $0.0010
промпт ~940/6000  · ответ ~193  · $0.0016
промпт ~2129/6000 · ответ ~671  · $0.0028
промпт ~3800/6000 · ответ ~1185 · $0.0049
```

Что бывает при переполнении:

- **промпт за бюджетом** — футер помечает `ПЕРЕПОЛНЕНИЕ`; автоматическое
  сжатие возвращает историю в бюджет, архивируя старые ходы;
- **лимит ответа** — `-max-tokens` (по умолчанию 4096) делится с
  reasoning-токенами: при слишком маленьком лимите ответ обрывается на
  полуслове (`finish_reason=length`), а если рассуждения съели весь бюджет,
  агент сообщает об этом ошибкой;
- **жёсткий лимит модели** — у glm-5.3-flash контекст 262144 токена. Одно
  сообщение больше лимита сжать нельзя (это «хвост», он остаётся дословно),
  и API отвечает `400 … maximum context length`. Флаг `-no-compact` отключает
  авто-сжатие, чтобы это поведение можно было показать: промпт растёт с каждым
  ходом, и на третьем гигантском сообщении запрос падает.

## Архив, а не удаление

Из промпта сообщения уходят, с диска — никогда. Событие `compact` помечает
диапазон `seq`, при перезапуске эти сообщения попадают в архив. Достать их
можно командой `/recall <текст>`; при желании архив легко выгружается в
`archive.jsonl.gz` или SQLite, не меняя формат активного лога.

Если модель сжатия недоступна, конспект сначала пробует построить чат-модель.
Каждая попытка ограничена 75 с — зависшая модель не съест весь бюджет хода и
оставит время запасной. Если не смогла и она, сырые сообщения всё равно
архивируются, а в конспект пишется пометка с обеими ошибками и ссылкой на
`/recall` — диалог не теряется.

## Команды чата

`/help`, `/exit`, `/new`, `/session [id]`, `/model [id]`, `/system`, `/tools`,
`/history`, `/tokens`, `/compact`, `/recall <текст>`, `/invariant [list | add |
change | remove | history]`, `/mcp [status | approvals | reset]`. `/session` без аргумента
показывает список сессий (текущая помечена `*`), `/session <id>` переключает на
другую сессию; `/model` без аргумента показывает список моделей, `/model <id>` меняет
чат-модель. `/strategy [имя [N]]` — стратегия контекста (см. раздел выше),
`/facts` — хранилище фактов, `/memory [clear <слой> | add <слой> ключ=значение]` —
слои памяти, `/branch [имя]` — чекпоинты и ветки диалога.
Ветки в списке сессий помечены родителем и точкой форка:
`← ветка от <id> (seq N)`, а `/branch` показывает у каждой ветки число
сообщений и точку ответвления.

## Интерфейс

- **Ответ печатается по мере генерации** (SSE-стриминг, `stream: true` +
  `stream_options.include_usage`): дельты контента летят в консоль сразу, без
  ожидания полного ответа. Reasoning-дельты (черновик мышления reasoning-моделей)
  печатаются серым построчно и стираются перед ответом — см. ниже. Если эндпоинт
  не поддерживает стрим, агент автоматически повторяет
  запрос в обычном режиме; частично напечатанный ответ при обрыве не
  дублируется.
- Пока модель думает, под строкой `agent> ` крутится односимвольный спиннер
  `/ - \ |` (только в TTY; в `-script`-режиме — сообщение каждые 10 с, пока
  стрим молчит).
- **Рассуждения модели** (reasoning-дельты) печатаются там же серым, построчно:
  видно, что модель думает, но как только начинается ответ, блок стирается
  (курсор поднимается ровно на столько строк, сколько напечатано, — перенос по
  ширине терминала считается вручную, поэтому лишние строки не задеваются).
  Так рассуждения не остаются на экране и не прокручивают консоль; в
  `-script`-режиме и при выводе не в TTY они не печатаются вовсе, а флаг
  `-no-reasoning` отключает их и в TTY — это нужно для записи демо-видео.
- **Ввод** в TTY — собственный lineEditor в сыром режиме (`readline.go`):
  ↑/↓ — история запросов (хранится между запусками), ←/→, Ctrl-A/E, Ctrl-U/W,
  Backspace, Ctrl-C — отменить строку. Пока модель отвечает, Ctrl-C отменяет
  текущий ответ и возвращает к промпту (сигнал превращается в отмену
  `context`), а не завершает процесс; выход — Ctrl-D на пустой строке или
  `/exit`. Отрисовка учитывает перенос длинных
  строк: перед каждой перерисовкой курсор поднимается на первую экранную
  строку ввода, и ввод стирается целиком (`\x1b[J`), поэтому длинный запрос
  не «размножает» промпт по экрану; ширина терминала берётся из
  `TIOCGWINSZ`. Раскладка позиции курсора — чистая функция `wrapLayout`
  (покрыта тестом).
- После каждого ответа — строка статистики: модель, оценка промпта против
  бюджета, токены последнего ответа, активное окно и архив, размер конспекта,
  вызовы API и стоимость; если промпт вышел за бюджет, добавляется
  `ПЕРЕПОЛНЕНИЕ`. Детали — `/tokens`, токены по сообщениям — `/history`.
- Вызовы инструментов и **сжатие** печатаются строкой `  ↳ …`; срабатывание
  сжатия видно сразу: «сжатие контекста: сообщения seq 1..4 → архив, конспект
  ~100 ток., промпт теперь ~584 ток.», а в статистике растёт «архив N сообщ».
