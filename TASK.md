# День 13. Состояние задачи — конечный автомат

Задача как машина состояний поверх агента: этап, текущий шаг, ожидаемое
действие. Ключевое правило дня: **переход проверяется кодом до применения**,
а не только описан в промпте. Все прогоны — на `deepseek-v4-flash.`

## Что сделано

- **Автомат в `internal/task`.** Этапы `planning → execution → validation →
  done`; таблица разрешённых переходов — единственный источник истины в коде:
  `planning→execution`, `execution→validation`, `validation→execution`
  (возврат на доработку), `validation→done`. Из `done` выходов нет. Всё, чего
  нет в таблице, отклоняется с ошибкой — состояние не меняется.
- **Два гейта, оба в коде.** Первый: `planning→execution` возможен только при
  флаге «план утверждён», который ставит пользователь командой `/task approve`
  — у инструмента модели действия approve нет принципиально, утвердить план
  себе ассистент не может. Второй: задача на паузе не пропускает переходы;
  `/task resume` возвращает ровно на сохранённые этап и шаг.
- **Пауза — флаг поверх любого этапа.** Проверена на всех трёх незавершающих
  этапах (unit-тест `TestPauseOnEveryStage`); продолжение не требует
  повторных объяснений — состояние лежит в `task.json` рядом с журналом
  сессии и переживает перезапуск.
- **Состояние в каждом запросе.** Блок «Состояние задачи» идёт в системный
  промпт после слоёв памяти (~70–130 токенов): этап, шаг, ожидаемое действие,
  признак паузы и допустимые переходы. Без начатой задачи блока нет совсем.
- **Инструмент `task_transition`.** Модель запрашивает переход — код решает.
  Запрещённый, из паузы или без утверждённого плана возвращается модели как
  ошибка инструмента, поэтому отказ виден и модели, и в трейсе, и в журнале.
  Инструмент ленивый: пока задача не начата, его схемы в запросе нет, и
  обычный диалог платит за инструменты как раньше (~382 токена вместо
  ~643); схема появляется вместе с блоком задачи после `/task start`.
- **`/task` — ручное управление.** `/task` — состояние и история переходов,
  `/task start`, `/task approve`, `/task pause`, `/task resume`,
  `/task state <этап> [шаг]` (тоже через валидатор), `/task reset`. В
  `/context` добавлена строка «задача» с этапом и токенами блока.

## Проверка 1: юнит-тесты матрицы переходов

`internal/task/task_test.go`: все пары «из → в» — легальные проходят, каждая
нелегальная отклонена со словом «запрещён» и этап не изменился; гейт плана
(`TestPlanningNeedsApproval`); пауза блокирует и снимается на том же месте
(`TestPauseBlocksTransitions`, `TestPauseOnEveryStage`); персистентность
(`TestPersistence`); инструмент через `Execute` — отказ доходит модели как
текст ошибки (`TestTaskTransitionTool` в `internal/tools`).

## Проверка 2: демо-прогон и чекер

Сценарий `testdata/day13-demo.txt` — живой диалог, где пользователь прямо
просит нарушить порядок. Чекер `scripts/check_task.py` сверяет журнал сессии
с `task.json` и таблицей переходов (продублирована в чекере намеренно —
поверка кода заданием, а не самим собой). Прогон на `deepseek-v4-flash`:

```
planning → done        модель отказала в тексте, инструмент не вызывала
planning → execution   инструмент вызван — код отклонил: план не утверждён
применён:       planning → execution   — после /task approve
execution → validation модель отказала в тексте: пауза активна
применён:       execution → validation — после /task resume
применён:       validation → done
ОК: автомат задачи прошёл проверку по журналу (3 применено, 1 отклонено кодом)
```

Важная деталь, которую видно только в журнале: из трёх запрещённых переходов
код отклонил один — тот, где модель всё-таки вызвала `task_transition` до
`/task approve`. Два других модель отвергла сама, в тексте, не доводя до
инструмента: она читает блок задачи и таблицу переходов. То есть автомат
соблюдается на двух уровнях — модель объясняет отказ, а код гарантирует, что
запрещённый переход не применится, даже если модель попробует. Чекер считает
только отказы уровня кода, поэтому в его итоге «1 отклонено».

Все четыре проверки из задания покрыты одним прогоном: пауза на этапе,
продолжение без повторных объяснений, попытка недопустимого перехода, реакция
на запрещённый (модель объясняет отказ, этап не меняется).

## Ограничения

- **Пауза — только вручную.** У модели нет действия «поставить на паузу»:
  заморозка и продолжение — решения пользователя, инструмент сознательно их
  не отдаёт.
- **`/task state` — тот же валидатор.** Ручной переход пользователя проходит
  через ту же проверку, что и запрос модели; «обойти таблицу» нельзя ни
  снизу, ни сверху.
- **Гейт проверки результата — правило промпта, а не код.** Таблица переходов
  знает только порядок этапов: что шаг действительно выполнен и с какими
  числами, код проверить не может. Поэтому в блок задачи и в описание
  инструмента добавлено правило: в `validation` переходить только когда
  результаты шага зафиксированы в ответе, иначе перечислить, чего не хватает,
  и дождаться ответа пользователя. Соблюдение видно на демо-прогоне глазами;
  чекер его не проверяет.
- **Экстрактор памяти может не уложиться в лимит.** На `deepseek-v4-flash`
  два хода из двенадцати закончились строкой «весь лимит (4096 ток.) ушёл на
  рассуждения, ответа нет»: модель потратила весь `-max-tokens` на reasoning.
  Профиль и слои памяти от этого не меняются (старый профиль остаётся), но
  факт из реплики в память не попадает. Лечится `-max-tokens` побольше или
  моделью без длинных рассуждений.
- **История — не журнал.** Переходы пишутся в `task.json` (кто и когда), но
  не отдельным событием в `session.jsonl`; чекер сопоставляет журналы вызовов
  инстру с файлом. Если понадобится аудит в самом журнале — добавить событие
  `task` по образцу `memory`.

## Воспроизведение

```bash
# живой прогон демо (провайдер считает запросы в окне 60 с — отсюда пауза
# между ходами; MODEL/SCRIPT_DELAY переопределяют модель и паузу). Модель
# недетерминирована, поэтому для видео каст синтезируется из удачного
# прогона ниже, а не из живого.
MODEL=deepseek-v4-flash SCRIPT_DELAY=45s \
  scripts/day13-demo.sh /tmp/day13-video

# синтез каста из удачного прогона (без новых вызовов модели) и сборка видео
python3 scripts/run_to_cast.py /tmp/day13-run-ok/demo/session.jsonl /tmp/day13-demo.cast
python3 scripts/render_cast.py --cast /tmp/day13-demo.cast \
  --out video/автомат-задачи-день-13.mp4 \
  --title "День 13 · конечный автомат задачи" \
  --subtitle "переходы проверяет код до применения, а не промпт" \
  --cards testdata/day13-cards.json

# проверка автомата по журналу
python3 scripts/check_task.py /tmp/day13-run-ok/demo
```

Видео: 59 с, 1352x970, 8 fps, без аудио. Каст собирается детерминированно
скриптом `scripts/run_to_cast.py` из лога удачного прогона — живые записи
на `deepseek-v4-flash` нестабильны (модель иногда не доводит сценарий до
`done`). Карточки — `testdata/day13-cards.json`.
