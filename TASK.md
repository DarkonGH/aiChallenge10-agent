# День 15. Устаревание и конфликты памяти

Долговременная память не должна копить противоречия. У каждой записи есть
время последней записи; новый факт с тем же ключом **заменяет** старый, а не
ложится рядом. Замена фиксируется в журнале «что было, что стало», старые
значения не попадают в текущий промпт, а после завершения задачи рабочая
память очищается кодом — долговременная остаётся.

## Что сделано

- **Время записи ставит код.** У `memory.Entry` появилось поле `updated_at`
  (RFC3339). Модель его не присылает: `Apply` проставляет время в момент
  применения диффа, поэтому час записи не зависит от того, что модель
  придумала в JSON. В промпте и `/memory` время печатается компактно
  (`[21.11 18:20]`), чтобы было видно, какая версия новее.
- **Замена по ключу, а не вторая запись.** `mergeEntryChanged` сравнивает
  ключ без учёта регистра и ё/е. При совпадении значение заменяется; если
  входящая запись объективно старше сохранённой, она отбрасывается как
  `stale`. Накопительные слои (`decisions`, `knowledge`) тоже заменяются по
  ключу, а не дублируются: «выбрали другой подход» обновляет запись, история
  остаётся в журнале. Ведущая дата в ключе решения отбрасывается кодом
  (`2026-11-21 · итог` → `итог`): дата уже хранится в `at`, а в ключе она
  создавала бы вторую запись вместо замены.
- **Журнал «было → стало».** `Apply` возвращает `[]Change` с видом
  `add/update/remove/evict`, ключом, старым и новым значением. Те же изменения
  пишутся событием `memory` в `session.jsonl`; `/memory history [ключ]`
  показывает их с временем, `-print-session` — при разборе лога офлайн.
  Ручные `/memory add` и `/memory clear` журналируются тем же способом.
- **Очистка после задачи — код.** При первом переходе `task_transition` в
  `done` реестр инструментов вызывает `Agent.TaskDone`: `working` очищается
  через `ClearWithChanges`, удаления попадают в журнал, `decisions` и
  `knowledge` не трогаются. Это не правило промпта: модель не может «забыть»
  очистить рабочую память.
- **Проверка промпта, а не самоотчёт.** `/memory prompt` печатает ровно тот
  блок, который `Compactor.MemoryBlock()` отдаёт в системный промпт. Если
  старого значения нет в файлах памяти, его нет и в блоке; проверять ответ
  модели на «я не помню старого» не нужно.
- **Правила экстрактора.** В `memorySystemPrompt` добавлено: `working` —
  временная карточка задачи, изменяемые факты (срок, бюджет, статус) идут тем
  же ключом с новым значением; отмена — `null`; `decisions` — накопительный
  список, изменение той же темы заменяет значение; не создавать ключи
  «старое значение» и не переносить временные данные в долговременные слои.

## Проверка 1: юнит-тесты

- `internal/memory` — замена по ключу пишет `update` с `old`/`new` и непустым
  `updated_at`; более поздняя запись побеждает, ранняя отбрасывается как
  `stale`; удаление и очистка journalятся; `decisions` сохраняют дату решения,
  даже когда значение обновляется; `Render` не содержит старого значения.
- `TestDescribeChanges` — человекочитаемая пара «было → стало» для всех видов.
- `internal/history` — журнал изменений переживает переоткрытие сессии,
  `PrintSessionLog` печатает `15 декабря → 20 декабря`.
- `internal/agent` — `TestTaskDoneClearsWorkingMemory`: после `TaskDone`
  `working` пуст, `decisions` на месте, в журнале есть `remove` со старым
  значением.
- `internal/tools` — `TestTaskDoneHook`: hook срабатывает только на входе в
  `done`, не на `execution`/`validation` и не повторно.

`gofmt -l .` пусто, `go vet ./...` чисто, `go test ./...` — все пакеты ok,
`go build` — успешно.

## Проверка 2: демо-прогон и чекер

Демо `scripts/day15-demo.sh`: переезд офиса, в памяти четыре изменяемых факта.
Сначала они заданы, затем по ходу диалога меняются:

| факт | было | стало |
|---|---|---|
| срок | 15 декабря | 20 декабря |
| парковка | нужна, 20 машин | требование отменено |
| вариант | коворкинг | готовый офис на Пулковском шоссе |
| бюджет | 300 000 ₽/мес | 350 000 ₽/мес, затем 330 000 ₽/мес по договору |

После каждого изменения ассистенту задаётся вопрос об актуальном значении;
в конце — сводка всех четырёх. Отдельно показаны `/memory history` и
`/memory prompt`. Затем задача проходит `planning → execution → validation →
done`; на `done` код очищает `working`, а `decisions` с итогом переезда
остаются.

Чекер `scripts/check_memory_conflicts.py` читает журнал и файлы памяти
независимо от ответов модели:

```
ходов с вопросом об актуальном значении: 5
изменений памяти в журнале: 24
целевых ключей с заменой/удалением: 4 из 4; всего изменённых ключей: 8
журнал «было → стало»: ok
устаревших ответов: 0
задача: этап done
working после завершения: 0 записей
очистка working: после done (done 2026-11-21T18:27:01+03:00, пусто 2026-11-21T18:27:01+03:00)
долговременная память: decisions 1, knowledge 0
старые значения в текущей памяти: 0
ИТОГ: ok
```

Счётчик устаревших ответов — это ответы, где старое значение названо как
актуальное. Упоминание «было 300 000» или «парковка отменена» устареванием не
считается: это история, а не текущее состояние.

## Ограничения

- **Экстрактор — модель.** Он может не заметить изменение или выбрать другой
  ключ; тогда код заменит запись только при совпадении ключа. В демо ключи
  заданы явно, поэтому замена детерминирована; в свободном диалоге это
  вероятностный слой, а не гарантия.
- **Время — момент применения, а не «когда факт стал истинным».** Если
  пользователь говорит о прошлом («раньше срок был 15 декабря»), запись
  получит текущее время, даже если описывает старый факт. Защита — правила
  экстрактора: историю не сохранять как актуальный факт.
- **Старые значения остаются в журнале и истории диалога.** Требование дня —
  чтобы они не попадали в **текущий блок памяти**; для аудита журнал обязан
  их хранить. `/memory prompt` показывает именно блок промпта, а не весь лог.
- **Очистка привязана к переходу в `done`.** Штатный путь — `task_transition`
  модели; ручной `/task state done` меняет автомат напрямую и hook инструмента
  не вызывает. Это сознательно: команда пользователя — отдельный уровень
  управления, а не «модель попросила завершить задачу».
- **Ручная правка файлов.** `working.json` и `long.json` можно поправить
  редактором; журнал ведётся для изменений через агент и команды, а не для
  внешних правок.

## Воспроизведение

```bash
# сборка
go build -o agent .

# демо: 4 меняющихся факта, локальный экстрактор qwen2.5:14b,
# задача доходит до done и очищает working
scripts/day15-demo.sh

# независимая проверка: замены, устаревшие ответы, очистка
python3 scripts/check_memory_conflicts.py /tmp/day15-demo

# каст из сохранённого прогона: команды не попадают в session.jsonl
python3 scripts/run_to_cast.py /tmp/day15-demo/demo/session.jsonl /tmp/day15-demo.cast \
  --commands testdata/day15-commands.json
python3 scripts/render_cast.py --cast /tmp/day15-demo.cast \
  --out video/устаревание-памяти-день-15.mp4 \
  --title "День 15 · устаревание и конфликты памяти" \
  --subtitle "замена по ключу, журнал «было → стало», очистка после done" \
  --cards testdata/day15-cards.json
```

Видео: 124 с, 1352x970, 8 fps, без аудио. Каст собирается
детерминированно из сохранённого прогона; команды и их вывод добавляются из
`testdata/day15-commands.json`, потому что в `session.jsonl` команд нет.
