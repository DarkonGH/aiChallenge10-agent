# День 19. Композиция MCP-инструментов: search → summarize → save_to_file

## Задание

Создать несколько MCP-инструментов на одном сервере и собрать из них
пайплайн: первый получает данные, второй их обрабатывает, третий сохраняет
результат. Проверить автоматическое выполнение цепочки и передачу данных
между инструментами. Затем сломать цепочку: второй инструмент возвращает
ошибку, первый — пустой результат. Агент должен вести себя предсказуемо:
не выдавать несуществующий результат, не вызывать следующий инструмент на
пустых данных и ясно сообщать, на каком шаге и почему цепочка остановилась.
Результат — приложение, видео и код.

## Что сделано

- `cmd/mcp-pipeline` — отдельный MCP-сервер на официальном Go SDK с тремя
  инструментами: `search`, `summarize`, `save_to_file`.
- `internal/pipeline` — общие типы данных (`Item`, `SearchResult`,
  `SummaryResult`, `SaveResult`). Локального оркестратора в агенте больше
  нет: цепочку строит модель.
- `main.go` — `run_pipeline` удалён. Три инструмента pipeline остаются
  обычными MCP-инструментами в `/tools`, модель вызывает их сама и передаёт
  `items` из `search` в `summarize`, а `summary` — в `save_to_file`.
- `internal/config/config.go` — правила 6 и 7 системного промпта: при пустом
  результате или ошибке не выдумывать данные и не продолжать цепочку;
  передавать между шагами только реальные результаты предыдущего шага.
- `main.go` — флаг `-workdir` и песочница модели: по умолчанию
  `~/goagent-work`, переопределяется `AGENT_WORK_DIR`. Внутри — `notes/` и
  `reports/`; MCP-корни `MCP_FS_ROOT`, `PIPELINE_SEARCH_ROOT` и
  `PIPELINE_OUT_DIR` выводятся из неё.
- `internal/workspace` — единая проверка путей: только относительные пути
  внутри workdir, запрет `..`, абсолютных путей и выхода через symlink;
  фильтры секретов, скрытых файлов и бинарников.
- `internal/mcp` — правило `deny_names` для `fs.read_file`, чтобы секреты
  нельзя было прочитать даже внутри разрешённого каталога.
- `mcp.json` — сервер `pipeline`; `testdata/day19-mcp.json` — отдельный
  конфиг только с ним для демо.
- `run.sh` — собирает `bin/mcp-pipeline` вместе с остальными серверами.
- `testdata/day19-notes` — четыре локальные заметки, по которым работает
  `search`. Сеть не используется.
- `scripts/day19-demo.sh` и `scripts/check_day19.py` — воспроизводимое демо
  и независимая проверка ручной цепочки.
- `testdata/day19-chat.txt` и `testdata/day19-cards.json` — реплики для
  демо и карточки для видео.

## Рабочий каталог модели

Модель не должна читать исходники репозитория и домашний каталог целиком.
У неё один sandbox:

- по умолчанию `~/goagent-work`;
- переопределяется флагом `-workdir` или переменной `AGENT_WORK_DIR`;
- при старте создаются `notes/` и `reports/`;
- `search` рекурсивно читает текстовые файлы внутри workdir, `save_to_file`
  пишет только в `reports/`;
- `MCP_FS_ROOT`, `PIPELINE_SEARCH_ROOT` и `PIPELINE_OUT_DIR` выставляются
  из workdir, поэтому filesystem- и pipeline-серверы видят тот же корень.

`internal/workspace.Resolve` проверяет путь лексически и после
`EvalSymlinks`: `..`, абсолютный путь или symlink за пределы workdir
отклоняются. Скрытые файлы и каталоги, бинарники с NUL-байтом и секреты
(`.env*`, `*.pem`, `*.key`, `*.p12`, `id_rsa*`, `id_ed25519*`,
`credentials*`, `secrets*`) не попадают в `search`. Для `fs.read_file`
добавлено правило `deny_names`, чтобы секрет нельзя было прочитать и через
filesystem-сервер; `list_directory` может показать имя, но содержимое
прочитать нельзя.

## MCP-сервер pipeline

Имя сервера — `goagent-pipeline`, версия 1.0.0, транспорт — stdio. Это один
процесс, в котором живут все три инструмента.

| Инструмент | Вход | Выход |
|---|---|---|
| `search` | `query`, `path` (подкаталог), `limit` (по умолчанию 5), `empty` | `query`, `root`, `count`, `scanned`, `skipped`, `truncated`, `items` (`id`, `title`, `path`, `line`, `snippet`, `text`) |
| `summarize` | `items`, `max_sentences` (по умолчанию 5), `fail` | `count`, `summary`, `sentences`, `source_ids` |
| `save_to_file` | `path`, `content`, `format`, `fail` | `saved`, `path`, `bytes`, `sha256`, `format` |

`search` рекурсивно обходит workdir: `notes/`, `reports/` и другие
текстовые файлы (`.md`, `.txt`, `.go`, `.json`, `.yaml`, `.sh`, `.py` и
т.п.). Он ищет по всем словам запроса, сортирует документы по числу
совпадений, возвращает строку первого совпадения и сниппет вокруг неё, а не
первые 300 символов. Лимиты: 1 МиБ на файл, 2000 файлов и 20 МиБ суммарно;
при срабатывании лимита в ответе `truncated:true`. `path` сужает поиск до
подкаталога. `count=0` — это нормальный пустой результат, а не ошибка:
именно на нём останавливается цепочка. Флаг `empty:true` возвращает пустой
результат, не читая диск, — он нужен для воспроизводимой проверки сбоя.

`summarize` делает экстрактивное резюме без вызова LLM: для заметок берёт
предложения из `text`, убирает повторы и ограничивает их числом
`max_sentences`; для кода использует строки вокруг совпадения и формат
`path:line`. Пустой список `items` — ошибка шага 2: продолжать нечем. Флаг
`fail:true` имитирует сбой обработки.

`save_to_file` пишет только относительный путь внутри каталога вывода,
создаёт родительские каталоги и считает SHA-256. Абсолютный путь и выход
через `..` отклоняются. Пустой `content` — ошибка шага 3. Флаг `fail:true`
имитирует сбой сохранения.

Каталоги задаются переменными окружения:

- `PIPELINE_SEARCH_ROOT` — корень рекурсивного `search`; основной процесс
  выставляет его в workdir. Устаревший алиас — `PIPELINE_NOTES_DIR`;
- `PIPELINE_OUT_DIR` — куда `save_to_file` пишет файлы; основной процесс
  выставляет `<workdir>/reports`, по умолчанию
  `~/.local/share/goagent/pipeline/reports`.

## Как модель строит цепочку

Локального `run_pipeline` нет. Модель видит три отдельные схемы и сама
решает, в каком порядке их вызвать:

```json
mcp_pipeline_search({"query": "MCP", "limit": 5})
```

`search` возвращает `items` с полным `text`. Модель передаёт этот массив в
следующий вызов:

```json
mcp_pipeline_summarize({"items": [...], "max_sentences": 5})
```

Затем готовое поле `summary` попадает в `content`:

```json
mcp_pipeline_save_to_file({
  "path": "mcp-summary.md",
  "format": "markdown",
  "content": "Резюме по 2 документам:\n- ..."
})
```

Правила поведения:

1. `search` вернул `count=0` или пустой `items` — цепочка останавливается на
   шаге 1; `summarize` и `save_to_file` не вызываются.
2. `summarize` вернул ошибку или пустое резюме — цепочка останавливается на
   шаге 2; `save_to_file` не вызывается.
3. `save_to_file` получил пустой `content` — ошибка шага 3; файл не
   создаётся.
4. Модель не подставляет документы, предложения или пути, которых не было
   в предыдущем результате.

В демо увеличен `-max-tool-chars` до 6000, иначе результат `search` с
полными `text` обрезается в промпте и модель вынуждена делать лишние
поиски. Это не часть протокола, а настройка демонстрации.

## Сценарии сбоев

| Сценарий | Флаг | Поведение |
|---|---|---|
| Нормальная цепочка | — | search → summarize → save_to_file |
| Пустой поиск | `search.empty=true` | `count=0`, шаги 2 и 3 не вызываются |
| Ошибка обработки | `summarize.fail=true` | ошибка шага 2, `save_to_file` не вызывается |
| Ошибка сохранения | `save_to_file.fail=true` | ошибка шага 3, файл не создаётся |
| Пустой текст | `save_to_file.content=""` | ошибка шага 3, сохранять нечего |

Пустой результат — не ошибка инструмента, а сигнал остановиться. Ошибка
шага 2 — не повод вызывать шаг 3 «на всякий случай». В обоих случаях
модель объясняет пользователю, где именно оборвалась цепочка, не придумывая
документы, резюме или файл.

## Демо

```bash
bash scripts/day19-demo.sh
```

Скрипт собирает `bin/mcp-pipeline` и `goagent`, копирует заметки из
`testdata/day19-notes` в `/tmp/day19-demo/work/notes`, запускает агента с
`-workdir /tmp/day19-demo/work` и `testdata/day19-mcp.json`, а отчёт пишет в
`/tmp/day19-demo/work/reports`, затем запускает checker.

Ключевые строки успешного хода:

```text
goagent> Найди в рабочем каталоге материалы про MCP, сделай краткое резюме и сохрани его в mcp-summary.md.
  ↳ mcp_pipeline_search({"query":"MCP","limit":5}) → ... {"count":2,...}
  ↳ mcp_pipeline_summarize({"items":[...],"max_sentences":5}) → ... {"count":2,"summary":"Резюме по 2 документам:...
  ↳ mcp_pipeline_save_to_file({"path":"mcp-summary.md",...}) → ... {"saved":true,...}
Готово. Цепочка: search → summarize → save_to_file.
```

Пустой поиск:

```text
  ↳ mcp_pipeline_search({"query":"MCP","empty":true}) → ... {"count":0,"items":[]}
Шаги 2–3 (summarize, save_to_file): не вызывались.
```

Ошибка второго шага:

```text
  ↳ mcp_pipeline_search({"query":"MCP","limit":5}) → ... {"count":3,...}
  ↳ mcp_pipeline_summarize({"fail":true,"items":[...]}) → ошибка инструмента mcp_pipeline_summarize: ...
Цепочка остановилась на втором шаге.
```

В демо модель сама вызывает `mcp_pipeline_search`, `mcp_pipeline_summarize`
и `mcp_pipeline_save_to_file`, без локального макроса. В первом сценарии
она один раз находит два документа, передаёт их в резюме и сохраняет
`mcp-summary.md` (772 байта). Во втором и третьем не пытается подставить
выдуманные данные и объясняет остановку.

- в успешном сценарии порядок `search → summarize → save_to_file`,

- `search.count >= 2`, `summary` непустой, `saved=true`, а `content`

  `save_to_file`;
- ошибочный сценарий: `summarize` после `search`, `fail=true`, нет
  `save_to_file`, текст ошибки содержит «тестовый сбой»;
- файл `mcp-summary.md` существует, содержит «Резюме» и «MCP»; в
  `reports/` ровно один файл;
- в логе есть вызовы всех трёх инструментов и нет `run_pipeline`.

## Ограничения

- `search` — простой лексический поиск по текстовым файлам workdir, без
  индекса и семантики; ранжирование — по числу вхождений. Для демонстрации
  композиции этого достаточно.
- `summarize` — экстрактивное резюме, без LLM. Оно не пересказывает текст
  своими словами, а выбирает предложения или строки кода; это делает
  поведение воспроизводимым и не зависящим от модели.
- `save_to_file` пишет только внутри `PIPELINE_OUT_DIR` (`<workdir>/reports`).
  Это защита от path traversal и symlink-выхода, а не полноценная песочница
  ОС: процесс по-прежнему может читать то, что ему разрешил пользователь.
- Флаги `empty`/`fail` — тестовые. Они нужны, чтобы сбои можно было показать
  без поломки реальных данных.
- Ручная цепочка зависит от того, видит ли модель полный результат
  `search`. При стандартном `-max-tool-chars 4000` JSON обрезается и модель
  может делать лишние поиски; в демо поэтому используется 6000.
- Модель может ошибиться в порядке вызовов или передать неполный `items`.
  Это и есть предмет проверки: код больше не гарантирует порядок, он только
  даёт инструменты и проверяет аргументы.
