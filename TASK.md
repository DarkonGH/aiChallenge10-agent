# День 18. Планировщик из чата, MCP и накопление данных

## Задание

Добавить в приложение планировщик, который по расписанию запускает сбор
данных. MCP-сервер должен уметь получать данные, сохранять их и отдавать
накопленное за период. Планировщик вызывает инструменты через MCP, сохраняет
результат каждого запуска и по расписанию строит отчёт по **всем** замерам,
а не только по последнему. Проверить несколько запусков подряд, накопление
между запусками и итоговый отчёт. Результат — приложение, видео и код.

## Что сделано

- `cmd/mcp-forex` — отдельный MCP-сервер на официальном Go SDK.
- `internal/forex` — клиент Coinbase spot, append-only JSONL-журнал и
  агрегированный отчёт.
- `internal/scheduler` — цикл `fetch_fx` → `save_tick` → `read_period` →
  отчёт. Поддерживает режим по числу запусков и режим по времени; сводка
  может считаться параллельно, чтобы не сдвигать следующий замер.
- `main.go` — инструмент `run_forex_schedule` для чата. Пользователь пишет
  обычную просьбу, модель выбирает аргументы, код проверяет их и запускает
  планировщик. Тот же бинарь сохраняет и старый CLI-режим `-schedule-*`.
- `main.go` — второй инструмент `run_tool_schedule`: повторяет один из
  разрешённых инструментов (`calc`, `mcp_rates_currency_rate`,
  `mcp_forex_fetch_fx`) и возвращает результаты всех запусков. Набор закрыт
  кодом, произвольный MCP-инструмент подставить нельзя.
- `internal/mcp/client.go` — `Manager.CallTrusted`: внутренний вызов MCP без
  guard, чтобы планировщик получал чистый JSON, а не обёртку
  `<untrusted_tool_output>`. Проверка аргументов и allowlist остаются.
- `internal/mcp/process_unix.go` — MCP-серверы запускаются в отдельной process
  group, чтобы `Ctrl-C` в агенте не убивал их вместе с прерванным ходом.
  Если сессия всё же закрылась, `Manager.Call` перезапускает сервер по его
  конфигу и повторяет вызов; в ошибку добавляется `stderr` сервера.
- `mcp.json` — сервер `forex` с тремя инструментами; `run.sh` собирает
  `bin/mcp-forex`.
- `testdata/day18-mcp.json` — отдельный конфиг только с `forex` для демо.
- `scripts/day18-chat.sh` — чат-сценарий: просьба, 24 запуска, две сводки,
  финальный отчёт и checker.
- `scripts/check_day18_chat.py` — независимая проверка чат-сценария.
- `scripts/day18-demo.sh` и `scripts/check_day18.py` — старый CLI-сценарий
  на шесть запусков.
- `testdata/day18-chat.txt` — реплика пользователя для демо.
- `testdata/day18-cards.json` — шесть карточек для видео.

## MCP-сервер forex

Источник: публичный Coinbase spot `https://api.coinbase.com/v2/prices/USD-RUB/spot`.
Ключ не нужен, ответ — обычный JSON. Это валютная пара, а не биржевой
Forex-терминал; значение может не меняться каждую секунду.

Инструменты:

| Инструмент | Вход | Выход |
|---|---|---|
| `fetch_fx` | `base`, `quote` (по умолчанию USD/RUB) | `base`, `quote`, `rate`, `fetched_at`, `source` |
| `save_tick` | замер (`base`, `quote`, `rate`, `fetched_at`, `source`) | `saved`, `total` |
| `read_period` | `from`, `to`, `quote` | `count`, `ticks` |

Хранилище — append-only JSONL. Каждый запуск добавляет одну строку; старые
замеры не перезаписываются. Путь задаётся `FOREX_STORE`, по умолчанию
`data/day18/forex.jsonl`.

## Чат-сценарий

Пользователь пишет:

```text
Запусти проверку курса USD/RUB каждые 5 секунд, сохраняй результаты.
Каждую минуту выводи сводку по всем замерам. Заверши проверку через 2 минуты.
```

Модель вызывает:

```json
run_forex_schedule({
  "pair": "USD/RUB",
  "interval_seconds": 5,
  "duration_seconds": 120,
  "summary_every_seconds": 60
})
```

Код проверяет диапазоны: `interval_seconds >= 1`, `duration_seconds` от 10
до 600, `summary_every_seconds` от 10 до длительности. Затем запускается
блокирующий цикл: диалог ждёт завершения, а строки запусков печатаются в
консоль по мере поступления.

Цикл:

1. `fetch_fx` получает курс.
2. `save_tick` добавляет замер в журнал и возвращает общее число записей.
3. По времени (раз в `summary_every_seconds`) `read_period` читает замеры
   от времени старта планировщика.
4. `forex.BuildReport` считает `count`, `min`, `max`, `avg`, `delta` и
   первый/последний замер. В отчёт попадают все запуски, а не последний.
5. Числовой отчёт сразу печатается, а текстовая сводка считается
   параллельно локальной моделью. Медленная сводка не сдвигает следующий
   замер.
6. В конце печатается финальный отчёт по всем замерам и итоговая строка.

Сводка — отдельный вызов `qwen2.5:14b` через `LLM_SUMMARY_*`. Модель получает
уже посчитанные агрегаты и пишет 2–3 предложения; она не пересчитывает
числа. Если сводка недоступна, числовой отчёт всё равно остаётся.

## Универсальный планировщик для разрешённых инструментов

`run_tool_schedule` — более узкий вариант для повторяющихся вызовов, когда
не нужно сохранять замеры и писать сводку. Модель передаёт:

```json
{
  "tool": "calc",
  "args": {"expr": "2+2"},
  "interval_seconds": 2,
  "duration_seconds": 10,
  "report_every_seconds": 10
}
```

Разрешены только три инструмента:

| `tool` | Что вызывает | Аргументы |
|---|---|---|
| `calc` | локальный калькулятор | `{"expr":"..."}` |
| `mcp_rates_currency_rate` | MCP `rates/currency_rate` | `{"currency":"USD","date":"20.11.2026"}` |
| `mcp_forex_fetch_fx` | MCP `forex/fetch_fx` | `{"base":"USD","quote":"RUB"}` |

Список задан map в `main.go`, а `CallTool` повторно проверяет имя. Модель не
может подставить произвольный сервер или destructive-инструмент. Для MCP
используется `CallTrusted`: это read-only инструменты, и guard-обёртка
сломала бы JSON, который планировщик возвращает модели.

`internal/scheduler.RunTool` печатает каждый запуск, промежуточный отчёт по
времени и итог, а в ответе возвращает все успешные результаты. Ошибки
отдельных запусков не останавливают цикл; если не удался ни один, модель
получает последнюю ошибку. Тесты — `internal/scheduler/tool_test.go`.

Проверено в чате: `calc` — 5 запусков `2+2 → 4`; `mcp_rates_currency_rate`
— 5 запусков USD 81,929; `mcp_forex_fetch_fx` — 5 запусков Coinbase spot.

## Ограничения

- Coinbase spot — публичный reference rate; между запусками он может не
  меняться. Для отчёта это нормально: важны накопление и агрегация.
- Нет ключа и нет гарантии SLA: при 429/5xx запуск считается неуспешным, в
  отчёт не попадает, планировщик продолжает работу.
- JSONL не чистится автоматически; для длительной работы нужен ротатор или
  SQLite.
- Планировщик вызывает MCP через `CallTrusted`, без guard модели. Это
  допустимо только для доверенного сервера `forex`.
- Время замера ставит клиент после ответа Coinbase, а не сервер.
- Сводка зависит от локальной модели: при её недоступности остаются только
  числа.
- Чат-инструмент блокирует диалог на время проверки; это сделано намеренно,
  чтобы не смешивать фоновые строки с вводом следующей реплики.
